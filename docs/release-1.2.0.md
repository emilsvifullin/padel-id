# Padel ID 1.2.0 — порядок выпуска

Статус на 13.10.2026: не выпущено. Production не менялся: в базе 14 миграций,
API на версии 1.1.0. Выпуск начинается только после явного разрешения владельца.
Журналы прежних проверок — `verification/1.2.0-acceptance.md`.

## Условия перед началом

1. Все проверки CI зелёные на выпускаемом коммите: Backend, iOS (четыре
   конфигурации), Release.
2. Точка входа для мобильного интернета проверена владельцем на телефоне без
   VPN (Wi-Fi Алмател и МегаФон) и добавлена в сборку.
3. Владелец дал разрешение на выпуск в момент выполнения.

## Что нельзя менять

- `PADELID_GATEWAY_SECRET` — не заменять.
- Проект Shift Register, его DNS, конфигурация и данные — не трогать.
- `PADELID_MIN_CLIENT_BUILD` в этом выпуске остаётся прежним. Padel ID 1.1.0
  должен продолжать работать с новым сервером.

## Шаги

1. **Резервная копия.** `python3 ios/build/verification/refresh-release-backup.py`
   снимает дамп схем `public, private, auth, storage, supabase_migrations` в
   защищённую папку. Проверить, что дамп читается:
   `pg_restore --list <папка>/production.dump`.
2. **Сверка миграций.**
   `supabase db push --dry-run --linked --project-ref xnxhlfuncxyzdfdmqlkb`
   должен показать ровно двенадцать файлов, без seeds и roles:

   - `20261010160145_social_ecosystem.sql`
   - `20261010160723_sports_events.sql`
   - `20261010161418_private_games_and_waitlists.sql`
   - `20261011010023_clubs_catalog_booking_foundation.sql`
   - `20261011020756_apns_push_foundation.sql`
   - `20261011162115_coach_discovery_and_schedule.sql`
   - `20261011162125_private_avatar_storage.sql`
   - `20261011162259_moderation_content_review.sql`
   - `20261011163321_event_schedule_management.sql`
   - `20261012073216_club_news_feed.sql`
   - `20261012180722_group_owner_account_cleanup.sql`
   - `20261013093000_avatar_read_for_previous_client.sql`
3. **Миграции.** Та же команда без `--dry-run`. Не использовать reset, repair
   истории миграций и применение через MCP: оно назначает свои версии файлам.
4. **API.** Слить PR в `main`: Vercel выкатывает production из `main`. Между
   шагами 3 и 4 старый API работает с новой базой; аватары в это время
   отдаются только новой версией API, поэтому шаги идут подряд.
5. **Проверка production.** `https://api-padel.shiftregister.ru/v1/health?deep=1`
   возвращает `status: ok`, `database: ok` и коммит из `main`. Workflow
   «Production smoke» зелёный. Аватар открытого профиля загружается без
   заголовка авторизации (так его запрашивает 1.1.0) и с сессией (1.2.0).
6. **Сборка.** Workflow «Release» на `main` собирает `PadelID.ipa` и публикует
   GitHub Release с заметками `release-notes/1.2.0.md`. Проверка IPA —
   `scripts/ios/verify-ipa.sh`.
7. **Приёмка на iPhone** по `verification/iphone-1.2.0.md`.

## Совместимость с Padel ID 1.1.0

- Прежние маршруты API и форматы ответов сохранены, новые поля только
  добавлены.
- 1.1.0 запрашивает аватары без сессии. Хранилище становится приватным, но
  шлюз со своим секретом читает для такого запроса текущее фото игрока,
  который не скрыт (`avatar_read_for_previous_client`). Скрытые профили,
  удалённые и заменённые фото не отдаются. Запрос с сессией всегда идёт по
  строгим правилам 1.2.0 (видимость, блокировки, действующая сессия).
- Остаточное отличие от правил 1.2.0: заблокированный игрок, запросив фото без
  сессии, получит его, как и в 1.1.0 сегодня. Это закрывается при отключении
  1.1.0.
- Отключение 1.1.0 — отдельное решение позже: поднять
  `PADELID_MIN_CLIENT_BUILD` до 3 (анонимная выдача аватаров прекращается
  сразу) и удалить политику `avatars: gateway read for the previous client`
  новой миграцией.

## Откат

- До шага 3 откатывать нечего.
- После шага 3: новые таблицы и функции не мешают старому API; откат схемы —
  только восстановлением из копии шага 1 и только по решению владельца.
- После шага 4: вернуть предыдущий deployment в Vercel. Новая схема с прежним
  API совместима, кроме аватаров (прежний API читает публичный адрес
  хранилища).

## Что не входит в выпуск

- Push через APNs: сборка устанавливается через SideStore с бесплатным Apple
  ID. Флаг `PADELID_PUSH_ENABLED` остаётся `NO`.
- Фотографии в публикациях, собственное бронирование кортов.

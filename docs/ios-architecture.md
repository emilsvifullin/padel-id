# Padel ID iOS — architecture & contracts

This document is the single source of truth for how the iOS client is built.
Every feature must follow it so the app reads as one product.

## Platform & toolchain

* SwiftUI app, **iOS 26.0+**, iPhone only, portrait. Built with **Xcode 26.6**
  (iOS 26 SDK) on GitHub Actions `macos-26` runners. Project generated by
  XcodeGen from `ios/project.yml` (sources are picked up automatically by
  folder: `ios/PadelID`, `ios/PadelIDTests`, `ios/PadelIDUITests`).
* **Swift 6 language mode** with `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`
  and approachable concurrency. Consequences:
  * Every type is `@MainActor` by default. UI, view models, `AppModel`,
    `APIClient`, stores are main-actor classes — that is intended.
  * Pure data types (API models, enums, helpers used from `@Sendable`
    closures) are declared `nonisolated` and `Sendable` (see
    `Core/Models/Models.swift`). New plain data types must do the same.
  * Never call main-actor code from a `@Sendable`/background closure. Avoid
    `DispatchQueue` callbacks; use `async`/`await`. If a framework calls back
    on the main queue, wrap with `MainActor.assumeIsolated`.
  * No `Task.detached`. Use `Task { }` (inherits main actor) and `.task {}`.
* **No third-party dependencies.** Only Apple frameworks (SwiftUI, Charts,
  PhotosUI, Network, UserNotifications, BackgroundTasks, Security).
* The UI language is **Russian only** (`CFBundleDevelopmentRegion = ru`).
  Write all user-facing strings in Russian directly in code (no
  localization tables). Use correct typography: «ёлочки», em dash —, non-breaking
  where useful, `ё` where it belongs. Pluralize with `Format.plural`/`Format.count`.

## Navigation

* `MainTabView` has three tabs: **Padel ID** (`HomeView`), **Матчи**
  (`MatchesView`), **Игроки** (`PlayersView`, `role: .search`). Each tab root
  owns a `NavigationStack` and calls `.padelRoutes()` on its root content so
  every shared destination works from every tab.
* Shared push routes (`App/Routes.swift`): `Route.player(UUID)`,
  `.match(UUID)`, `.rating(UUID)`, `.dna(UUID)`, `.playerMatches(UUID)`,
  `.stats(UUID)`, `.insights`. Navigate with
  `NavigationLink(value: Route.match(id)) { … }`.
* Required view signatures (exact):
  * `PlayerProfileView(playerId: UUID)` — Features/Players
  * `MatchDetailView(matchId: UUID)` — Features/Matches
  * `RatingDetailView(playerId: UUID)` — Features/Rating
  * `DNADetailView(playerId: UUID)` — Features/DNA
  * `PlayerMatchesView(playerId: UUID)` — Features/Matches (confirmed match history of any player; for the current user it is the same list)
  * `StatsDetailView(playerId: UUID)` — Features/Home
  * `InsightsView()` — Features/Home (current user's insights)
  * `MatchEditorView(request: MatchEditorRequest)` — Features/MatchEditor
  * `AccountView()` — Features/Settings
  * `OnboardingFlow()` — Features/Onboarding
* Sheets above the tabs are opened through `AppModel`:
  * `app.matchEditor = .blank` or
    `MatchEditorRequest(mode: .create(partner: card, opponents: []))` or
    `MatchEditorRequest(mode: .edit(detail))`.
  * `app.isAccountPresented = true` (account & settings).
* Switch tabs with `app.selectedTab = .matches`.

## Data loading

* `AppModel` (environment object: `@Environment(AppModel.self) private var app`)
  exposes `api: APIClient`, `cache: ResponseCache`, `outbox: Outbox`,
  `connectivity`, `me: Me?`, `dataRevision`, `actionCount`, `isOnline`,
  `refreshMe()`, `dataDidChange()`, `signOut(everywhere:)`,
  `resetLocalState(notice:)`, `flushOutbox()`, `recoveryKeyToShow`.
* Screens load data with `Resource<T>` (`Core/Storage/Resource.swift`),
  cache-first:
  ```swift
  @State private var home = Resource<HomeResponse>(cacheKey: CacheKey.home) { .get("v1/home") }
  …
  .task(id: app.dataRevision) { await home.load(using: app) }
  .refreshable { await home.load(using: app) }
  ```
  Render: value → content (and `StaleDataBanner(error:)` when `isStale` and an
  error is set: the offline banner for network errors, the error message plus
  «Показаны сохранённые данные.» otherwise);
  no value + error → `ErrorStateView(error:retry:)`; otherwise `LoadingView()`.
  Use `CacheKey` constants (App/AppModel.swift) for cache keys.
* After any successful mutation call `app.dataDidChange()` so other screens
  reload; update the local `Resource` with `replace(with:)` from the response.
* Requests: `try await app.api.send(endpoint, as: T.self)`; `sendVoid` for 204.
  Build endpoints with `Endpoint.get(path, query:)`, `Endpoint.json(method,
  path, body, idempotencyKey:, retryable:)`, `Endpoint.empty(...)`. Paths are
  relative without a leading slash: `"v1/matches/\(id.uuidString.lowercased())"`.
  Bodies: Swift `Encodable` structs (encoder converts camelCase → snake_case)
  or `[String: …]` dictionaries with snake_case keys, or `AnyEncodable(JSONValue)`.
* Errors are `APIError` (`message` is user-facing Russian text, `code` is the
  server code, `isNetwork` for offline). Show inline/footer text for forms,
  `.alert` for actions. Never show raw codes.
* Offline mutations: create match, confirm, dispute and feedback must go
  through the outbox when offline or on a network failure
  (`PendingOperation`, `app.outbox.enqueue`, then `Task { await app.flushOutbox() }`).
  Show the pending state in the UI ("Отправится при подключении").
  Editing, cancelling, profile and account changes require a connection: when
  offline, disable the action and explain why.

Server rules worth mirroring in the UI (the server stays authoritative):
* 4 distinct onboarded players, 2 per team, one `right` and one `left` per
  team; the current user must be one of them.
* Ranked matches: played within the last 14 days; friendly: 90 days; never in
  the future. A player can have ≤ 6 ranked matches per day.
* Valid set scores: 6–0…6–4, 7–5, 7–6 (tie-break points optional; if given,
  winner reaches 7 with a 2-point margin). Super tie-break (format
  `best_of_3_super_tiebreak`, only as set 3): first to 10, win by 2. Use
  `ScoreRules`.
* Only the creator edits/cancels; other participants confirm or dispute.
  Responses carry `version`; send it back. `version_conflict` → reload and
  show the current score.
* Feedback is possible for 14 days after confirmation, up to 2 strengths and
  1 improvement per player.

## Visual language

* Native first: system fonts (Dynamic Type text styles only; numerals use
  `.rounded` design + `.monospacedDigit()`), SF Symbols, `List`/`Form` where
  the content is a list or a form, standard navigation bars and toolbars,
  `.sheet` with detents for short tasks, `.confirmationDialog` for
  destructive choices, `.alert` for errors of actions.
* Backgrounds: `Color(.systemGroupedBackground)` for scroll screens with
  `SectionContainer` blocks; `List`/`Form` use `.insetGrouped`.
* Colors: `Theme.accent` (court blue), `Theme.ball` only for the level hero
  and DNA fill, `Theme.positive/negative/attention` for meaning. No other
  hard-coded colors.
* **Liquid Glass** is used deliberately, not decoratively: system bars and tab
  bar (automatic), toolbar buttons (automatic), floating primary action areas
  pinned to the bottom with `.safeAreaBar(edge: .bottom)` containing
  `GlassEffectContainer` and `.buttonStyle(.glassProminent)` /
  `.buttonStyle(.glass)`. Never apply `.glassEffect` to content cards or list
  rows; buttons inside forms use `.borderedProminent`.
* Results and failures of actions are spoken with `Announce.post(_:)` so
  VoiceOver users hear what happened.
* Spacing: `Theme.horizontalPadding` (20) side margins on scroll screens,
  `Theme.sectionSpacing` between sections, 12–16 inside containers.
  Touch targets ≥ 44 pt.
* Every screen supports Light/Dark, Dynamic Type up to accessibility sizes
  (no fixed heights for text; allow wrapping; use `ViewThatFits` or vertical
  stacks when horizontal layouts would truncate), VoiceOver (labels for
  icon-only buttons, combined row elements, headers marked with
  `.accessibilityAddTraits(.isHeader)`).
* Haptics with `.sensoryFeedback` on meaningful events (confirm success,
  dispute warning, selection changes in pickers).
* Empty states use `ContentUnavailableView` with one clear action at most.
* No placeholder copy, no "coming soon", no buttons without an action, no
  debug UI.
